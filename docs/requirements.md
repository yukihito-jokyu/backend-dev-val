# 要件定義書

## 1. システム概要

### 1.1 目的

本システムは、Go言語によるバックエンド開発の技術検証を目的としたTodo管理APIである。クリーンアーキテクチャに基づき、実務レベルの設計・実装パターンを習得する。

### 1.2 対象スコープ

既存のTodo CRUD APIに対し、以下の4機能を段階的に追加する。

| 優先度 | 機能                             | 概要                                 |
| ------ | -------------------------------- | ------------------------------------ |
| 高     | ページネーション・フィルタリング | 一覧取得のページング・検索・ソート   |
| 高     | ソフトデリート                   | 論理削除によるデータ復旧             |
| 中     | 期限管理（Due Date）             | Todoに期限を設定し、ステータスを判定 |
| 中     | タグ・カテゴリ機能               | 多対多リレーションによるタグ付け     |

### 1.3 用語定義

| 用語           | 定義                                                                 |
| -------------- | -------------------------------------------------------------------- |
| Todo           | ユーザーが管理するタスク。タイトル・説明・完了状態・期限・タグを持つ |
| ソフトデリート | データを物理削除せず、削除フラグで管理する方式                       |
| タグ           | Todoに付与するラベル。複数Todoに紐付け可能                           |
| 期限切れ       | 現在日時がdue_dateを超過している状態                                 |

## 2. 機能要件

### 2.1 ページネーション・フィルタリング

#### 2.1.1 ページネーション

- 一覧取得APIでページネーションをサポートする。
- パラメータ: `page`（ページ番号、デフォルト1）、`limit`（1ページあたりの件数、デフォルト20、最大100）。
- レスポンスにメタ情報（総件数、総ページ数、現在のページ）を含める。
- `page`が範囲外の場合は空の結果を返す（エラーにしない）。

#### 2.1.2 フィルタリング

- `completed`（bool）: 完了/未完了でフィルタ。
- `due_before`（日付）: 期限が指定日以前のTodo。
- `due_after`（日付）: 期限が指定日以降のTodo。
- フィルタ未指定時は全件対象。

#### 2.1.3 ソート

- `sort` パラメータでソート対象フィールドを指定: `id`、`title`、`due_date`、`created_at`。
- `order` パラメータで昇順/降順を指定: `asc`（デフォルト）、`desc`。
- デフォルトは `id` 昇順。

### 2.2 ソフトデリート

#### 2.2.1 削除方式

- 削除対象のTodoの `deleted_at` に現在日時を設定する（物理削除しない）。
- 削除済みデータは通常の一覧取得から除外する。

#### 2.2.2 削除済みデータの操作

- 削除済みTodoの一覧取得API: `GET /api/todos/trash`。
- 削除済みTodoの復元API: `POST /api/todos/:id/restore`。
- 削除済みTodoの物理削除API: `DELETE /api/todos/:id/permanent`。
- 復元時は `deleted_at` をNULLに設定する。

#### 2.2.3 制約

- 既存の `DELETE /api/todos/:id` の動作をソフトデリートに変更する。
- 通常の一覧取得・個別取得では削除済みデータを含めない。
- 削除済みデータに対する更新操作は `NotFoundError` を返す。

### 2.3 期限管理（Due Date）

#### 2.3.1 期限の設定

- Todoに `due_date`（TIMESTAMP）を追加する。
- 作成・更新時に `due_date` を指定可能（任意項目）。
- 未指定の場合は `null` を許容する。

#### 2.3.2 ステータス判定

- レスポンスに `is_overdue`（bool）フィールドを追加する。
- `due_date` が存在し、現在日時が `due_date` を超過している場合に `true`。
- `completed` が `true` の場合は `is_overdue` を `false` とする（完了済みは期限切れ扱いしない）。

#### 2.3.3 バリデーション

- `due_date` が指定された場合、有効な日時フォーマット（RFC3339）であること。
- 過去の日時の指定は許可する（バリデーションエラーにしない）。

### 2.4 タグ・カテゴリ機能

#### 2.4.1 タグのCRUD

- タグの作成: `POST /api/tags`（name必須、一意制約）。
- タグの一覧取得: `GET /api/tags`。
- タグの更新: `PUT /api/tags/:id`。
- タグの削除: `DELETE /api/tags/:id`（紐づくTodoとの関連も削除）。

#### 2.4.2 Todoへのタグ付け

- Todoの作成・更新時に `tag_ids`（int64の配列）を指定可能。
- 指定されたタグIDが存在しない場合は `NotFoundError` を返す。
- Todoのレスポンスに `tags`（タグオブジェクトの配列）を含める。

#### 2.4.3 タグによるフィルタリング

- 一覧取得APIの `tag_id` パラメータで特定タグが付与されたTodoをフィルタ。

## 3. 非機能要件

| 項目                 | 要件                               |
| -------------------- | ---------------------------------- |
| データベース         | PostgreSQL                         |
| API形式              | REST、JSONリクエスト/レスポンス    |
| エラーレスポンス     | `{"error": "message"}` 形式        |
| ページネーション上限 | 1ページ最大100件                   |
| タグ名の最大長       | 255文字                            |
| タグ名の一意性       | 同名タグの作成は `ValidationError` |

---

## 4. 既存機能への影響

| 既存機能     | 影響                                                 | 対応                       |
| ------------ | ---------------------------------------------------- | -------------------------- |
| Todo一覧取得 | レスポンス形式変更（メタ情報追加、タグ配列追加）     | 後方互換性を維持しつつ拡張 |
| Todo個別取得 | レスポンスに `due_date`、`is_overdue`、`tags` を追加 | フィールド追加のみ         |
| Todo作成     | `due_date`、`tag_ids` をリクエストに追加             | 任意項目として追加         |
| Todo更新     | `due_date`、`tag_ids` をリクエストに追加             | 任意項目として追加         |
| Todo削除     | ソフトデリートに変更                                 | API仕様は変更なし          |
